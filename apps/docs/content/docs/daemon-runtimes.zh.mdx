CodeOPC 记录和协调工作，连接上来的电脑负责执行：电脑上的**守护进程**（daemon）领取运行，再调用本机安装的 AI 编程工具。

## 概念区分

- **守护进程**是运行在一台电脑上的 CodeOPC 后台程序。它负责连接服务器、发现本机工具、领取运行和回传结果。
- **运行时**代表一个工作区可以使用的具体执行环境。它对应一台电脑，以及这台电脑上的一款 AI 编程工具或自定义运行时配置。

例如，一台电脑装了 Claude Code 和 Codex，连接了两个工作区，守护进程就为每个工作区各注册一条 Claude Code 运行时和一条 Codex 运行时。重启守护进程会更新原有记录，不会为同一个组合反复创建新运行时。

## 执行位置与数据边界

本地运行时调用的 AI 编程工具、这些工具自己的登录凭据和本地代码目录，都留在连接的电脑上。CodeOPC 服务器不替本地工具执行命令，也不会自动上传整个工作目录。

为了让团队能够协作，服务器会保存任务、评论、智能体配置、运行上下文、执行记录和智能体写回的结果。这些内容可能包含智能体主动读取并写入回复的代码片段或其他项目上下文。

<Callout type="warning">
"本地执行"不等于所有 secret 都只存在本机。智能体的自定义环境变量和 MCP 配置保存在服务器侧，展示时受敏感信息规则限制；自定义环境变量会在执行时发送给运行时。
</Callout>

### 开机自启 [#autostart]

用 CLI 启动的守护进程默认不会随电脑重启自动恢复。需要的话，为当前 profile 登记开机自启：

登记的命令是这个 profile 的 `multica daemon start --foreground`，由系统在登录时拉起：Windows 写入当前用户的 Run 注册表项，macOS 写入 `~/Library/LaunchAgents` 下的 LaunchAgent，Linux 写入 systemd 用户单元，没有 systemd 用户会话时改用 XDG autostart 条目。使用命名 profile 时加 `--profile <name>`，每个 profile 单独登记。

- 只有 `enable` 会创建登记。`multica daemon start` 不会自己登记，只在没有登记时提示一行；已有 CodeOPC 创建的登记时，它会顺手更新其中的可执行文件路径，升级或挪动 CLI 后不必重新 `enable`。
- 在 macOS 和 Linux 上，登录会话只带上 `enable` 时 shell 里的 `PATH`，shell 导出的其他变量（API key、`HTTPS_PROXY` 等）都不会带过去。守护进程配置用 `multica config set` 持久化，其他变量放进用户级环境。
- Linux 的 systemd 用户单元在登录时启动。要在开机后不登录也启动，按 `enable` 输出的提示运行 `loginctl enable-linger <用户名>`。
- `multica daemon stop` 只停止当前进程，不删除登记。
- 同一位置已有不是 CodeOPC 创建的文件（例如你自己写的 systemd 单元）时，`enable` 和 `disable` 都会拒绝修改它。
- Desktop 拉起的守护进程由 Desktop 管理，`daemon start` 不会为它提示或更新登记。

## 派发与在线状态

运行时注册后保持连接。新运行入队时，服务器通知对应的守护进程；守护进程也会定期轮询，防止连接中断时漏掉通知。所以运行时在线、又有空闲容量时，运行通常立即开始。

守护进程每 15 秒发送一次心跳。服务端综合心跳与连接状态判断运行时是否在线；守护进程意外退出后，最迟约 3 分钟会被判为离线。**运行时**页面在失联的头 5 分钟里显示"最近失联"，之后显示"离线"。

运行时离线时：

- 已经排队的运行等待运行时恢复，不会转到其他电脑。只有运行时心跳缺席超过重连宽限期，**并且**这条运行自己也已排队满这么久，它才会失败。运行时只是忙的话，积压会一直保留；指派给已离线运行时的工作，也有完整的一个宽限期可以等。
- 正在执行的运行不会马上失败。运行时心跳缺席超过重连宽限期（`MULTICA_RUNTIME_RECONNECT_GRACE`，默认 3 小时）后，它们才以 `runtime_offline` 失败；符合条件的任务或对话运行可以自动重试。
- 守护进程重新启动后，会重新注册运行时，并回收上一次没有正常结束的运行。
- 离线超过 7 天且没有活跃用户智能体或未完成任务的运行时会自动清理，已归档智能体和任务历史会保留。旧自定义配置未绑定机器时，仅保留配置创建者本人机器上的实例，直到管理员选择归属机器。

## 并发限制

一台守护进程默认最多同时执行 20 次运行；每个智能体默认最多同时执行 6 次。实际并发取两者中的较小值。

等待直接修改模式本地目录的运行不占用守护进程执行槽位。开始前会重新获取槽位；等待期间仍由守护进程持有，关闭和更新时的安全检查仍会计入这些运行。

达到上限后，新运行继续排队。单个智能体的并发数在智能体设置中调整，整台电脑的上限用 `MULTICA_DAEMON_MAX_CONCURRENT_TASKS` 调整。并行执行会同时占用机器性能、工具账号额度和同一工作目录。

运行消耗的 token、费用和失败情况在[统计](/analytics)页按工作区汇总；单条运行时的 token 用量也可以用 `multica runtime usage <runtime-id>` 查看。

Claude Code 和 Codex 运行时的页面上还有**额度**：CLI 账号在套餐的 5 小时会话和每周窗口里已经用了多少、什么时候重置，以及用量是否跑在时间前面。这些数据由 CLI 在执行任务时上报，反映的是这个运行时最近一次运行时的状态。API Key 账号没有套餐额度。

## 本机 MCP 配置 [#local-mcp]

智能体没有保存 MCP 配置时，CodeOPC 不向工具传任何 MCP 设置，工具照常读取这台电脑上它自己的配置。

智能体有 MCP 配置后（哪怕是空配置），CodeOPC 会为每次运行生成一份专用配置交给工具，例如 Claude Code 会以严格模式只加载这份配置。为了不让本机已有的服务器因此失效，守护进程会在运行时所在的电脑上读取该工具的用户级 MCP 配置，再和智能体的配置合并。同名服务器按以下顺序取第一个：

1. 智能体 **MCP** 标签页中由 CodeOPC 管理或从工作区 MCP 库分配的服务器；
2. 工具的用户级配置文件；
3. 仅 Claude Code：已启用的 Claude Code 插件自带的 MCP 服务器。插件取自 `~/.claude/settings.json` 的 `enabledPlugins`，读取插件目录下的 `.mcp.json` 和插件清单里声明的 MCP 文件。

| 工具 | 读取的用户级配置 |
|---|---|
| Claude Code | `~/.claude.json` 的 `mcpServers`，以及已启用插件的 MCP 服务器 |
| Codex | `$CODEX_HOME/config.toml`（默认 `~/.codex/config.toml`）的 `mcp_servers` |
| Cursor Agent | `~/.cursor/mcp.json` 的 `mcpServers` |
| OpenCode | `$XDG_CONFIG_HOME/opencode/opencode.json`（默认 `~/.config/opencode/opencode.json`）的 `mcp` |
| OpenClaw | `$CLAWDBOT_CONFIG_PATH`，或 `$OPENCLAW_STATE_DIR/openclaw.json`（默认 `~/.openclaw/openclaw.json`）的 `mcp.servers` |
| CodeArts | `~/.codeartsdoer/codearts_cli.json` 或 `codearts_cli.jsonc` 的 `mcp` |

CodeBuddy、Kimi CLI 和 Pi 启动时会自己加载用户级配置，并与 CodeOPC 下发的配置合并，守护进程不再预先合并，否则同一个服务器会启动两次。CodeBuddy 遇到同名服务器时以 CodeOPC 下发的为准。表外的其他工具只收到智能体的配置。

合并在运行时所在的电脑上完成，本机服务器的命令、URL、请求头和环境变量不会上传。智能体 **MCP** 标签页的"从运行时继承"一栏只显示服务器名称、传输方式、来源和是否启用；被智能体同名服务器覆盖的会标为"已由 CodeOPC 覆盖"。本机配置文件无法解析时，守护进程记一条警告日志，这次运行只使用智能体的配置。

### Cursor 的 MCP 登录 [#cursor-mcp-login]

Cursor 按项目目录保存 MCP 的 OAuth 登录，而每次运行都有自己的目录。因此 daemon 会在运行时所在电脑上为每个 Cursor 智能体保留一份登录文件，即 CodeOPC 配置目录下的 `cursor-mcp-auth/<agent-id>/mcp-auth.json`，并让每次运行都链接到它。对 Mobbin 这样的服务登录一次，这个智能体之后在这台电脑上的运行都能用。它和你自己各个 Cursor 项目里的登录分开，运行不会把你那边挤下线。这个智能体在这台电脑上的所有运行都会用到它，包括其他成员触发的运行。

智能体有 MCP 配置时，每次运行都有自己的 Cursor 数据目录，运行在那里的 `mcp-auth.json` 就是这个链接。没有 MCP 配置时，运行使用你自己的 Cursor 数据目录（`~/.cursor`，或 daemon 的 `CURSOR_DATA_DIR`）和其中配置的 MCP 服务；daemon 只把 Cursor 在 `projects/` 下为运行目录保存的 `mcp-auth.json` 链接到智能体的登录文件。运行的目录被清理时，这个链接会一并删除。

没有 MCP 配置时，有两种运行不做链接，因为它们对应的 Cursor 项目你自己也在用，链接会替换掉你在那里的登录：在项目本地目录里原地工作的运行，以及目录外层套着一个 git 仓库的运行，例如主目录下的 dotfiles 仓库（Cursor 会把这个仓库当作项目）。这些运行使用 Cursor 在该目录下已有的登录，运行记录里也不会给出登录命令；需要时自己在该目录里执行 `cursor-agent mcp login <server>` 登录。

如果某个服务仍需登录，运行记录里会写明是哪个服务，并给出要在运行时所在电脑上执行的命令。有 MCP 配置的智能体，例如：

```bash
cd ~/.multica/cursor-mcp-auth/<agent-id>/login/workdir && CURSOR_DATA_DIR=~/.multica/cursor-mcp-auth/<agent-id>/login/cursor-data cursor-agent mcp login mobbin
```

没有 MCP 配置的智能体，命令使用你自己的 Cursor 数据目录：

```bash
cd ~/.multica/cursor-mcp-auth/<agent-id>/user-login/workdir && CURSOR_DATA_DIR=~/.cursor cursor-agent mcp login mobbin

text
<你的命令> <你的固定参数> <CodeOPC 的协议参数> <Agent 的自定义参数>
```

带子命令的 wrapper 靠这个顺序工作。命令是 `ccms start q36` 时，工具先看到 `start q36`，在 CodeOPC 的 `-p` 等参数到达之前选好子命令；这类 wrapper 只接受这一种顺序。

这里的参数以前追加在最后。多数 flag 形式的命令在两种位置下解析结果相同，但区分全局 flag 和子命令 flag 的命令会在意位置。已经配置了带固定参数的 profile 的，升级后请发起一次运行，确认它仍能正常启动。

另外：

- **冲突时以 CodeOPC 的值为准。** 如果固定参数设置了 CodeOPC 也会设置的 flag，CodeOPC 的值排在后面并最终生效。最典型的是：在 Agent 上选择的模型会覆盖 profile 里固定的 `--model`。若要为所有人固定模型，请把 Agent 的模型字段留空。
- **协议关键 flag 会被忽略。** `-p`、`--output-format`、`--input-format`、`--permission-mode` 以及其他协议族的对应 flag 会从固定参数中被剔除，因为覆盖它们会切断 daemon 与工具之间的通信。子命令和其他位置参数始终原样传递。

## Qoder Cloud Agents 远端运行时

Qoder Cloud Agents 通过远端会话执行分配的任务。CodeOPC 服务端管理桥接进程，复用现有守护进程任务协议，无需用户启动本地守护进程。

### 准备工作

- 需要工作区管理员权限。每个工作区只有一个 Qoder 连接。
- 创建 Qoder 个人访问令牌（PAT）、至少一个运行环境，以及要在 Qoder Cloud Agents 中使用的智能体。模型、工具和 skill 都在 Qoder Cloud Agents 中的远端智能体上配置，不在 CodeOPC 中配置。
- 自托管部署需在服务端设置 `MULTICA_VCS_SECRET_KEY`：一个 base64 编码的 32 字节密钥，重启前后必须保持不变。未设置时，**添加**菜单中不会出现 Qoder Cloud Agents。

### 连接 Qoder

1. 在**运行时**页面点击**添加**，在**云服务**下选择 **Qoder Cloud Agents**。
2. 在**服务区域**中选择签发 PAT 的站点：**国际站**（qoder.com）或**中国站**（qoder.com.cn）。PAT 只在签发它的站点有效；如果被拒绝，可点击按钮改用另一站点重试。
3. 将 PAT 粘贴到**个人访问令牌**。验证通过后会从 Qoder 加载**运行环境**列表；只有一个环境时自动选中，否则手动选择。
4. 可选：展开 **GitHub 仓库授权**，为智能体需要克隆的每个仓库填写仓库 URL 和令牌。智能体只能克隆这里授权过的仓库。
5. 可选：展开**执行设置**，设置并发运行数（默认 3，最多 10）和运行超时（默认 60 分钟，可设 5 到 240 分钟）。
6. 点击**连接**。Qoder Cloud Agents 会出现在运行时页面的云服务分组中，几秒内上线。

### 添加智能体

在运行时页面打开 Qoder Cloud Agents，点击**用它创建智能体**；也可以照常创建智能体并选择 Qoder 运行时。在智能体表单的 **远端智能体**中选择远端智能体。已有智能体可在**Qoder Cloud Agents** 标签页中修改关联的 Qoder Cloud Agents 智能体或默认仓库。多个 CodeOPC 智能体可以共用同一个连接，各自关联不同的 Qoder Cloud Agents 智能体。

连接凭证加密保存，在工作区内共享。管理员管理连接，成员可以选择可访问的 Qoder Cloud Agents 智能体。项目选择仓库和起始分支；创建编码会话时，对应仓库的令牌会传给 Qoder Cloud Agents。保存后的 PAT 不会返回浏览器。

管理员可以在 Qoder Cloud Agents 页面编辑连接和仓库；点击**暂停**停止下发新任务，凭证和智能体保留；点击**断开连接**删除已保存的令牌、移除该运行时并解绑其智能体。

### 运行方式

超出并发上限的任务会排队等待。同一任务的后续运行会在上一会话空闲时继续使用该 Qoder 会话。智能体可以设置默认仓库，在任务所属项目未绑定仓库时使用。智能体会被要求以任务标识命名分支，并在 PR 标题前加上任务标识，以便 PR 自动关联到任务。

首版支持任务运行、聊天、担任小队队长、通过智能体创建任务、进度同步、取消和基于持久化记录的恢复。模型、工具和 skill 在 Qoder 中配置。任务和聊天消息里的附件和图片会交给远端会话，包括 PDF 和 Office 文档，每个文件不超过 5 MB；更大的文件不会传过去，智能体只知道有这些文件。聊天中智能体用 DeliverArtifacts 交付的文件（每个不超过 10 MB）会作为附件随回复发出。暂不支持本地目录，也不支持从 CodeOPC 创建远端 Qoder Cloud Agents 智能体。运行时页面分别展示远端运行时和电脑。

独立桥接进程的配置与限制见 [Qoder runtime README](https://code-opc.benlai.com/blob/main/server/cmd/qoder-runtime/README.md)。

## 运行时离线的排查

按以下顺序检查：

1. 运行 `multica daemon status`，确认守护进程已经启动。
2. 运行 `multica daemon logs -f`，查看登录、网络或工具检测错误。
3. 在同一运行环境中执行 `command -v <工具命令>`，确认守护进程能够找到它。
4. 打开 CodeOPC 的**运行时**页面，检查目标电脑和对应的 AI 编程工具是否显示在线。
5. 工具刚安装、路径刚修改或配置刚更新时，运行 `multica daemon restart`。
