Multica 在进程启动时读取环境变量。修改后通常需要重启对应的 API、Web 或守护进程。Docker Compose 的 `docker compose restart` 不会重新读取 `.env`，要用 `up -d` 重建容器才能生效。

本页按分组列出面向部署者的配置，测试变量和内部运行变量不在这里展开。完整部署步骤见[自托管快速上手](/self-host-quickstart)。

## 生产环境最小配置

```dotenv
DATABASE_URL=postgres://user:password@postgres:5432/multica?sslmode=require
JWT_SECRET=<long-random-secret>
APP_ENV=production
FRONTEND_ORIGIN=https://code-opc.benlai.com
MULTICA_APP_URL=https://code-opc.benlai.com
MULTICA_PUBLIC_URL=https://api.code-opc.benlai.com

dotenv
MULTICA_CLAUDE_PATH=/opt/bin/claude
MULTICA_CLAUDE_ARGS=--max-turns 40
```

### DeepSeek Harness 的 profile 安装

`MULTICA_DSH_PROFILE_BUNDLE` 指定 `multica` profile 缺失时要安装的 bundle，多个候选用逗号分隔、按序尝试，每项可以是 npm 包名、目录或打包好的 tarball。该变量默认不设置。Multica 驱动的 `--stdio` 协议正是由这个 profile 提供，所以不设置时不会改动 DSH 的安装，守护进程会报告缺少 profile，不会注册一个不可用的运行时。

Multica 自己的桥接还没有发布到公共 npm registry，如何选取值见[安装智能体运行时](/install-agent-runtime)。这里填的东西会在没有二次确认的情况下装进每一台守护进程宿主的 DSH 家目录，请当作供应链决策来对待。

这项安装被刻意限制了范围：每个守护进程生命周期最多执行一次，只在探测确认 profile 确实缺失时执行；失败时会把包管理器自身的输出记入日志，且只有重启守护进程后才会重试。探测超时、或返回本守护进程不支持的协议版本时，只做报告，绝不覆盖安装：守护进程不会覆盖一个明显是刻意装上去的 profile。排查时在守护进程日志中搜索 `DSH runtime profile`；要撤销安装，删除 `$DSH_HOME/profiles/multica`（默认 `~/.dsh/profiles/multica`）。

`MULTICA_DSH_PLUGIN_PATH` 用于覆盖安装时解析 pnpm 的目录。`dsh plugin` 转发到的那个 pnpm 由 DSH Desktop 放在它私有的 runtime-commands 目录里，macOS 和 Windows 都是如此，守护进程会自动找到并加到 PATH 最前，较新版 Desktop 采用的带版本号目录结构也能找到。所以只有守护进程找不到的安装位置、或者你想让安装使用自己的 pnpm 时，才需要这个变量。一旦设置就完全取代自动查找：目录不存在时，安装会退回使用守护进程 `PATH` 上的 pnpm，不会用内置的那个。Linux 上没有 DSH Desktop，安装始终使用 `PATH`。

### Cursor 后台进程清理

Cursor 已验证的后台清理需要 Linux 6.9 及以上（进程组 pidfd）、macOS 内核对进程身份查询与 audit token 发信号的支持，或 Windows 上成功分配的嵌套 Job Object。在 macOS 上，每个进程都按内核校验的 PID version 发信号，不需要加入同一 session 的进程组；这些 macOS 接口是私有的，会在捕获时做探测。无法认领的后台启动会返回它原本的工具结果并回到普通的 idle watchdog，工具 watchdog 为 `0` 时同样如此。已经认领的工作在清理无法确认时会继续算作执行中。当工具 watchdog 设为 `0` 时则完全没有这个边界：已认领的后台工作只要还活着就一直让运行处于执行中，此时运行仅受 `MULTICA_AGENT_TIMEOUT` 约束，而它默认也是 `0`。

运行正常结束时，被认领的 Cursor 后台进程同样会被停止，因此该次运行启动的后台服务不会有意留到收尾之后。macOS 可以通过保留的原始父进程身份识别后期产生的子进程，但无法证明中间进程在被观察到之前就已消失的那条链路。这类进程、离开被追踪进程组的工作，以及持续的归属或发信号错误，都可能留下残余的后台工作。未确认的清理会被记录下来，且永远不会换取一次"清理成功"的恢复窗口；不会仅凭数字 PID 或进程组就去杀掉未知进程。

### 守护进程配置的持久化

守护进程侧的常用配置也可以写入 `~/.multica/config.json`，不必依赖 shell 环境变量；命名 profile 的配置文件在 `~/.multica/profiles/<name>/config.json`：

支持的键：

| 键 | 默认值 | 说明 |
|---|---|---|
| `server_url` | `ws://localhost:8080/ws` | Multica API / WebSocket 地址 |
| `app_url` | 空 | 浏览器登录使用的 Web 地址 |
| `workspace_id` | 空 | 默认工作区 |
| `device_name` | 主机名 | 运行时列表中的设备名 |
| `runtime_name` | `Local Agent` | 运行时显示名 |
| `workspaces_root` | `~` 下按 profile 区分的路径 | 执行工作目录的根目录 |
| `max_concurrent_tasks` | `20` | 并发运行上限；`0` 或留空表示未设置 |
| `poll_interval` | `30s` | 运行轮询间隔 |
| `ws_claim_poll_interval` | `3m` | 健康 WebSocket 下 claim 安全轮询的上限，与 `poll_interval` 独立配置；Daemon 会应用向下抖动 |
| `heartbeat_interval` | `15s` | 心跳间隔 |
| `agent_timeout` | 不限制 | 单次执行的绝对时限 |
| `agent_idle_watchdog` | `2h` | 没有工具执行时的静默上限；`0s` 关闭守护进程的整套 watchdog，`agent_tool_watchdog` 也随之失效 |
| `agent_tool_watchdog` | 同 `agent_idle_watchdog` | 工具执行期间的静默上限；`0s` 表示守护进程的 watchdog 不会因工具静默而停止执行，此时执行只受 `agent_timeout` 限制，而它默认不限制 |
| `codex_semantic_inactivity_timeout` | 派生 | Codex 语义静默阈值。未设置时取 idle 与 tool watchdog 预算中较大的那个；tool 预算为 `0` 时回落到 idle 预算；只有整套 watchdog 关闭时才保留 Codex 自己的 `10m` |
| `codex_handshake_timeout` | `30s`；`thread/start`、`thread/resume`：`60s` | Codex app-server 启动握手上限；显式设置后会统一覆盖两类预算 |
| `disable_auto_update` | 跟随环境 | `true` 关闭自动更新；`false` 清除本地覆盖，回到环境变量或默认 |
| `auto_update_check_interval` | `6h` | 检查更新的间隔 |
| `disable_auto_reload` | 跟随环境 | `true` 让守护进程不再跟随磁盘上被替换的二进制；`false` 清除本地覆盖。与 `disable_auto_update` 分开解析 |

几条取值规则：

- duration 类键接受正的 Go duration（如 `10s`、`2h`），负值一律拒绝。只有 `agent_timeout`、`agent_idle_watchdog`、`agent_tool_watchdog` 还接受 `0s`：`agent_timeout` 设为 `0s` 表示明确关闭执行时限，两个 watchdog 键设为 `0s` 关闭什么见上表。
- 传空字符串清除已持久化的值，回到环境变量或内置默认，例如 `multica config set poll_interval ""`。
- `max_concurrent_tasks` 要求非负整数。
- 相对的 `workspaces_root` 值在保存时会转换为绝对路径。

## 观测与统计

| 变量 | 默认值 | 说明 |
|---|---|---|
| `DO_NOT_TRACK` | 空（默认开启遥测） | 设为 `1` 或 `true`（不区分大小写）后，停止首方匿名自托管遥测的采集与发送 |
| `ANALYTICS_DISABLED` | `false` | 设为 `true` 关闭 PostHog 上报 |
| `POSTHOG_API_KEY` | 空 | 不设置时统计上报关闭；接入自己的 PostHog 项目时填写 |
| `POSTHOG_HOST` | `https://us.i.posthog.com` | PostHog 地址 |
| `METRICS_ADDR` | 空 | Prometheus metrics 监听地址；空表示不启动 |
| `REALTIME_METRICS_TOKEN` | 空 | 保护 `/health/realtime` 的 bearer token |

首方自托管遥测每天按 UTC 发送一份部署级快照，固定且不可配置的地址为 `https://telemetry.multica.ai/v1/telemetry/events`。快照只包含正式发布版本、工作区数/去重成员数/活跃智能体数/过去 24 小时活跃守护进程数的分桶，过去 24 小时运行的开始、完成、失败和取消总数，以及过去 1、7、28 个完整 UTC 日内登录后打开过网页端或桌面端的成员数、亲自发起过智能体运行（分配、@、评论、聊天、手动运行或重跑；不含 autopilot 和智能体之间的委派）的成员数的分桶。成员只在本部署内计数，不会被识别。不会发送名称、邮箱或域名、IP、业务标识符、主机或设备信息、代码仓库、模型或 plugin、prompt/output、评论或聊天、文件路径、token/费用、凭据、错误文本、stack 或日志。此数据只用于了解自托管版本采用、部署规模区间、聚合使用量与成员活跃情况，不用于计费、授权、认证或安全决策。

`DO_NOT_TRACK` 与 `ANALYTICS_DISABLED` 相互独立：前者控制这份首方匿名快照，后者控制可选的 PostHog 集成。
